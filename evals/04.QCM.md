## Section 4 — Clean Code _(7 pts)_

### Selon les principes Clean Code, une fonction devrait :
_Q10 · QCS · 1 pt_

- [ ] Faire le plus de choses possible pour limiter le nombre de fonctions
- [ ] Faire une seule chose, et la faire bien
- [ ] Toujours retourner une valeur (jamais `void`)
- [ ] Avoir au minimum 3 paramètres pour être réutilisable

---

### Quel est le meilleur nom pour une variable contenant le délai maximum d'expiration d'une session (en secondes) ?
_Q11 · QCS · 1 pt_

- [ ] `t`
- [ ] `max`
- [ ] `sessionTimeoutSeconds`
- [ ] `theMaximumAmountOfSecondsBeforeTheSessionExpires`

---

### Lesquelles de ces pratiques sont recommandées par Clean Code ?
_Q12 · QCM · 2 pts — cochez toutes les bonnes réponses_

- [ ] Les commentaires doivent expliquer le **pourquoi**, pas le **quoi**
- [ ] Préférer moins de 3 arguments par fonction
- [ ] Commenter le code supprimé plutôt que de le supprimer
- [ ] Les noms doivent révéler l'intention
- [ ] Remplacer les "nombres magiques" par des constantes nommées

---

## Section 5 — SOLID _(7 pts)_

### Le principe **Open/Closed** (OCP) signifie qu'un module doit être :
_Q14 · QCS · 1 pt_

- [ ] Ouvert à la modification et fermé à l'extension
- [ ] Ouvert à l'extension et fermé à la modification
- [ ] Toujours abstrait et jamais instanciable
- [ ] Refactorisé à chaque nouveau besoin

---

### Le principe de **substitution de Liskov (LSP)** stipule que :
_Q15 · QCS · 1 pt_

- [ ] Les interfaces doivent être séparées en petites unités cohérentes
- [ ] Les modules de haut niveau ne doivent pas dépendre des modules de bas niveau
- [ ] Une sous-classe doit pouvoir remplacer sa classe parente sans altérer le comportement attendu
- [ ] Chaque classe doit avoir une seule raison de changer

---

## Section 7 — Object Calisthenics _(5 pts)_

### La règle "**Un seul niveau d'indentation par méthode**" vise avant tout à :
_Q21 · QCS · 1 pt_

- [ ] Rendre le code plus compact
- [ ] Forcer l'extraction de méthodes et réduire la complexité cognitive
- [ ] Interdire les boucles imbriquées pour des raisons de performance
- [ ] Rendre le code compatible avec tous les langages

---

### La règle "**Ne pas utiliser le mot-clé `else`**" encourage :
_Q22 · QCS · 1 pt_

- [ ] L'utilisation systématique d'opérateurs ternaires
- [ ] Les early returns et la clause de garde (guard clause)
- [ ] Le remplacement de tous les `if` par des `switch`
- [ ] L'utilisation de `try/catch` à la place

---

### Identifiez **toutes** les règles Object Calisthenics violées dans ce code. Pour chaque violation, nommez la règle.
_Q23 · Analyse de code · 3 pts_

```java
public class OrderProcessor {
  public double processOrder(Order order) {
    double total = 0;
    if (order != null) {
      if (order.getItems() != null) {
        for (Item item : order.getItems()) {
          if (item.isAvailable()) {
            if (item.getQuantity() > 0) {
```

## Section 8 — TDD _(7 pts)_

### Dans le cycle **Red → Green → Refactor**, l'étape "Green" consiste à :
_Q24 · QCS · 1 pt_

- [ ] Écrire le test le plus exhaustif et le plus complet possible
- [ ] Écrire le **minimum** de code de production pour faire passer le test
- [ ] Refactoriser le code pour améliorer sa structure
- [ ] Supprimer les tests qui passent pour ne garder que les tests en échec

---

### Le TDD apporte principalement :
_Q25 · QCS · 1 pt_

- [ ] Une couverture de code à 100% garantie automatiquement
- [ ] Une conception pilotée par l'usage et un filet de sécurité pour le refactoring
- [ ] La suppression du besoin de revue de code
- [ ] Des performances meilleures en production

---

### Lesquelles de ces affirmations sur le TDD sont **vraies** ?
_Q26 · QCM · 2 pts — cochez toutes les bonnes réponses_

- [ ] Les tests doivent être écrits **avant** le code de production
- [ ] On ne passe au test suivant que quand tous les tests précédents sont verts
- [ ] L'étape Refactor peut casser des tests existants
- [ ] Un bon test TDD documente le comportement attendu du système
- [ ] Le TDD garantit l'absence totale de bugs en production
